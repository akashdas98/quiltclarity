# 2. Strategic V2 Direction to Investigate — Not Pre-Approve

Investigate whether the evidence supports this broader strategic direction:

> **QuiltClarity becomes the comprehensive practical web utility system for quilting: the necessary calculators and planning tools quilters repeatedly need, plus deeper workflow solvers for jobs that remain painful even when ordinary calculators and existing quilting software are considered.**

This is a **hypothesis to validate**, not a predetermined product definition.

- a broad utility system;
- a smaller set of deeply integrated workflows;
- a hybrid;
- or another shape discovered through research.

# 3. Three Product Layers to Research

If the evidence supports the comprehensive-utility direction, investigate three complementary layers.

## Layer A — Commodity / Necessary Utility Completeness

Goal:

> **When a quilter has a common practical calculation or planning task, QuiltClarity should often be a credible place to solve it.**

This does not mean building every quilting calculator imaginable.

Research which utilities are necessary enough that their absence would make the product feel materially incomplete.

Commodity utility coverage does **not** need to be unique.

Its value can come from:

- search acquisition;
- trusted consistency;
- repeat use;
- project integration;
- reducing the need to leave QuiltClarity.

## Layer B — Integrated Leverage

Some tools may become materially better because QuiltClarity already knows project context.

Research where known project information can remove repeated work:

- quilt dimensions;
- fabrics;
- usable WOF;
- seam allowance;
- project cut requirements;
- stock/remnants;
- backing/batting/binding requirements;
- borders/sashing;
- component quantities;
- shopping quantities.

Integration should remove repeated entry when safe. It should not create hidden coupling or force every tool into a project.

## Layer C — Differentiated Workflow Solvers

Research multi-step jobs where the best realistic alternatives still leave meaningful manual work.

These are the strongest candidates for actual product differentiation.

For each candidate:

- define the complete user job;
- identify the best realistic alternative;
- reconstruct that alternative end-to-end;
- benchmark the same job;
- prove a meaningful segment has a rational reason to choose QuiltClarity.

Do not assume every complicated workflow deserves first-class product treatment.

# 4. The Central V2 Research Question

The research is **not**:

> “What features should we add?”

It is:

> **After V1.1 already solves its current external cut-list / fabric-reconciliation workflow, what combination of utility breadth, project integration, and additional underserved workflows would make QuiltClarity meaningfully more useful—and rationally preferable for a meaningful segment to the best realistic quilting alternatives?**

The research must answer:

1. What current V1.1 capabilities should remain unchanged?
2. What V1.1 capabilities should improve?
3. Which ordinary utilities are necessary for practical completeness?
4. Which existing capabilities should gain additional entry surfaces rather than separate new engines?
5. Which painful workflows remain materially underserved after considering the complete user choice set?
6. Which apparently attractive opportunities disappear once best-alternative adoption is considered?
7. What new categories/workflows were not anticipated by this brief?
8. What should V2 **not** become?

# 5. Mandatory Research Methodology

Use the latest supplied research playbook as the governing methodology.

The rules below are minimum requirements and should be expanded by the latest playbook where it is stricter.

## 5.1 Start From the Complete User Job

Before proposing a feature or workflow, define:

- target user;
- starting state;
- what information/material they already possess;
- desired end state;
- current steps;
- current manual work;
- constraints;
- what happens immediately after the result.

Do not begin with:

> “We should build a calculator for X.”

Begin with:

> “What recurring job is this person actually trying to finish?”

## 5.2 Pain Mining

Search current:

- Reddit quilting communities;
- quilting forums;
- specialist blogs/comments;
- publicly accessible social/community discussions;
- app-store reviews;
- product reviews;
- YouTube comments where useful;
- shared spreadsheets/tools;
- current calculator/tool discussions;
- search queries reflecting repeated manual work.

Look for phrases such as:

- “I made a spreadsheet…”
- “I calculate this every time…”
- “Does anyone have a tool for…”
- “I use graph paper…”
- “I have to use three calculators…”
- “The calculator doesn’t account for…”
- “How do I know if I have enough…”
- “How do I resize…”
- “Can someone check my math…”
- “I wish this app…”
- “I keep track of this manually…”

Triangulate. One post is not sufficient.

## 5.3 Manual Workaround Rule

A spreadsheet, homemade calculator, graph-paper process, or repeated manual calculation proves **pain**.

It does **not** prove a missing product.

Users may:

- be unaware of an existing solution;
- prefer familiar tools;
- resist learning a broader tool;
- refuse to pay;
- have discovered a workaround before a better product;
- be using an existing product imperfectly.

Treat the workaround as pain evidence only. Then separately prove the product gap.

## 5.4 Competitor Mapping by User Job

Search broadly.

A competitor is not only another “quilting calculator website.”

A realistic alternative may be:

- specialist web utility;
- mobile app;
- desktop quilting software;
- full visual quilt designer;
- spreadsheet/template;
- stash/project-management app;
- marketplace/pattern platform;
- manufacturer tool;
- generic cutting optimizer;
- broad hobby software;
- manual workflow that is actually easier than software adoption.

For each serious user job, identify the strongest 3–5 realistic alternatives.

## 5.5 Mandatory Competitor Set to Revisit

At minimum, re-check current offerings from the strongest known classes/products, including where still relevant:

- Quilt Geek / Designed to Quilt;
- QuiltSandwich;
- PreQuilt;
- Gibson Threads;
- NiftyFifty;
- Quiltler;
- Yard;
- QuiltFit;
- Quiltry / current stash-material planners;
- major specialist quilting-calculator sites;
- generic cut-list/stock optimizers when geometry overlap matters.

Also search for:

> **new entrants and major feature changes since the latest QuiltClarity research.**

Do not assume this list is complete. Competitors are discovered by the user job, not by brand memory.

## 5.6 End-to-End Competitor Reconstruction

For every serious competitor, reconstruct the same representative job from start to finish.

Record:

- user's starting state;
- setup required;
- data entry;
- whether the quilt/project must be recreated;
- learning burden;
- steps;
- calculations;
- output;
- remaining manual reconciliation;
- account/install requirement;
- free/paid boundary;
- export/print;
- project integration;
- repeated-use value;
- what happens next.

Do not substitute a feature matrix for this.

## 5.7 Source-as-Threat Rule

If a product's documentation is good enough that QuiltClarity research relies on it for:

- domain formulas;
- quilting practice;
- workflow understanding;
- cutting logic;
- edge cases;

then automatically escalate that product into serious competitive review.

Do not learn the domain from a product and simultaneously treat it as strategically irrelevant.

## 5.8 Best-Alternative / Adoption Test

For **every important target segment and every proposed flagship workflow**, ask:

> **If QuiltClarity did not have this feature/workflow, what is the best realistic solution this user could adopt?**

This includes products they do **not currently use**. It includes alternatives that change the user's upstream workflow.

Then compare:

1. current behavior;
2. proposed QuiltClarity path;
3. best realistic available alternative.

Ask:

> **Why is QuiltClarity materially preferable to simply adopting that alternative?**

Being outside an incumbent ecosystem is not itself a market gap.

## 5.9 Do Not Create Segments by Exclusion

Invalid segment definition:

> “People who do not use PreQuilt.”

Potentially valid segment definition:

> “People starting from an external cut list who need exact multi-remnant allocation and purchase-shortfall reconciliation, and for whom recreating the project in the best alternative adds materially more work without equivalent benefit.”

A segment must have:

- a real job;
- meaningful population;
- durable reason not to use the stronger substitute;
- rational reason to choose QuiltClarity after learning the alternative exists.

## 5.10 Segment-Capture Proof

Before declaring a product/workflow attractive, establish:

- the segment exists in meaningful numbers;
- their pain is recurring;
- their reason not to adopt the strongest substitute is real;
- QuiltClarity removes enough cost/friction/manual work;
- the segment does not collapse once alternatives are known.

Do not define an addressable market into existence.

## 5.11 Addressable Demand After Substitution

Do not estimate opportunity only from:

- problem prevalence;
- forum pain;
- search volume.

Ask:

> **How much demand remains realistically capturable after accounting for substitutes?**

Conceptually discount:

- users already well served;
- users likely to adopt a strong incumbent;
- users whose best alternative has less adoption friction than QuiltClarity;
- users whose workflow does not need the proposed extra depth.

This applies both to individual workflows and to the whole V2 product.

## 5.12 Direct Same-Job Benchmark

Every important reason-to-win claim must be tested on the same representative job where practical.

Examples:

- easier setup;
- fewer manual transformations;
- better stock reconciliation;
- more accurate calculation;
- better purchase decision;
- stronger integrated output;
- less re-entry;
- simpler cutting execution.

Do not infer differentiation from feature names.

If a claimed advantage cannot be verified, label it **unverified**. Do not use unverified differentiation to justify BUILD.

## 5.13 Whole-Product Best-Alternative Test

Do not apply adoption analysis only at the feature level.

V2 itself must pass:

> **Why would a quilter use QuiltClarity as a recurring practical utility system rather than adopting the strongest current general alternative?**

Compare whole-product:

- breadth;
- workflow depth;
- integration;
- setup;
- project recreation;
- correctness;
- explainability;
- price;
- account/install;
- speed;
- search discoverability;
- repeat use;
- print/export;
- project continuity.

Do not conclude:

> “QuiltClarity has more calculators, therefore it wins.”

Breadth only matters when it creates real user advantage.

## 5.14 Copy / Absorption Test

For every major differentiated V2 workflow:

> **If the strongest incumbent adds the headline feature tomorrow, does QuiltClarity still have a coherent reason to exist?**

Separate:

- entry wedge;
- commodity coverage;
- durable compounding advantages.

Potential durable layers to assess:

- integrated project model;
- accumulated trusted domain rules/tests;
- workflow depth;
- breadth;
- speed/frictionlessness;
- transparent assumptions;
- search footprint;
- repeat use/habit;
- brand trust;
- ability to reuse project context across tasks.

Do not bloat V2 merely to make copying harder.

## 5.15 Two-Proof BUILD Gate

Every major V2 product/workflow decision must pass two separate proofs.

### Proof A — Opportunity Proof

The job has:

- real pain;
- enough reachable/capturable demand;
- viable SERP/distribution path where SEO matters;
- worthwhile economics relative to burden.

### Proof B — Product Reason-to-Win Proof

For a meaningful segment:

> **QuiltClarity is materially preferable to the best realistic alternative.**

A high Opportunity Proof cannot rescue a failed Product Reason-to-Win Proof.

# 6. Product-Role Classification

Every serious candidate should be classified as one of:

## Commodity completeness

A normal useful capability users reasonably expect from a comprehensive quilting utility system. It may not differentiate QuiltClarity.

## Integrated leverage

A capability made materially better because QuiltClarity already knows relevant project context.

## Differentiated workflow

A multi-step painful job where the best realistic alternatives still leave meaningful unresolved work.

## SEO / reference surface

Useful searchable information that does not need to be a major interactive feature.

## Existing V1.1 capability — leave unchanged

Already good enough.

## Existing V1.1 capability — improve

Current product is useful but research identifies a justified improvement.

## Post-V2 candidate

Promising, but not justified for the current release.

## Reject

Insufficient need, weak capture, already solved well, excessive burden, or poor fit.

# 6.1 One Engine, Multiple Entry Surfaces Rule

Before creating a new domain engine, ask:

> **Is this actually another entry point into an existing V1.1 capability?**

Examples that might reuse the same underlying engine:

- how many pieces fit in a remnant;
- can these pieces fit the fabric I already have;
- how much more fabric do I need;
- fat-quarter feasibility;
- leftover allocation;
- pieces-from-fabric.

If multiple user jobs can safely share one calculation engine:

- reuse the engine;
- create distinct UX/search entry surfaces only when the user jobs are genuinely different.

Avoid duplicated business logic.

# 8. Painful Workflow Hypotheses — Research, Do Not Lock

The list below contains hypotheses only.

For each, classify:

- **CONFIRM**
- **MODIFY**
- **MERGE**
- **DEFER**
- **ELIMINATE**

Add stronger workflows discovered through pain mining.

## 8.1 Project-Wide Material Plan

Hypothesis:

Users calculate quilt-top fabric, borders, sashing, backing, batting, binding, and specialty units separately and manually combine them.

Potential integrated leverage:

> **known project context → connected material calculations → one shopping summary**

Research whether this is a meaningful workflow advantage or merely a prettier calculator bundle.

## 8.2 Pattern / Quilt Resize → Recompute Affected Quantities

Hypothesis:

Changing quilt dimensions or block size forces users to recalculate multiple dependent quantities.

Potential workflow:

> **known project structure + target change → recompute safe dependent quantities + warn where structure cannot be inferred**

Research whether enough can be specified safely without interpreting arbitrary pattern construction.

## 8.3 Backing Strategy Decision

Hypothesis:

The real job is not merely “how much backing?”

It may be:

> **Given quilt size, fabric widths, print direction, seam preferences, longarmer requirements, prices, and fabric availability, which backing strategy should I use?**

Compare only transparent valid candidates. Do not pretend one method is universally best.

## 8.4 Precut Planning Workflow

Hypothesis:

Users may start from:

- a precut bundle already owned;
- a desired quilt size;
- a required block/component.

Linked questions may include:

- what can this bundle make;
- how many packs are needed;
- what quilt size is possible;
- what extra yardage is required.

Research whether a connected workflow materially beats isolated conversion tables.

## 8.5 “How Do I Reach This Target Quilt Size?”

Hypothesis:

Given:

- block size/count;
- possible sashing;
- possible borders;

user wants a target finished size.

Potential solver:

> **suggest valid row/column, sashing, border, or block-size combinations and show consequences**

Research demand and trust boundaries.

## 8.6 Cutting-Plan Strategy Choice

Hypothesis:

One plan is not always best because users trade:

- lower fabric purchase;
- simpler cuts;
- fewer joins;
- larger useful leftovers;
- directional constraints;
- strip-friendly cutting.

Potential output:

- lower fabric;
- simpler cutting;
- preserve larger leftovers;

only if research shows real user value.

Do not expose optimizer modes merely because engineering can.

## 8.7 Deeper Pattern Math Checking

V1.1 already includes structured pattern yardage comparison.

Research whether a meaningfully broader verification job remains:

- cut-list consistency;
- component quantity checking;
- cross-checking materials;
- designer/pre-publication math audit.

Do not assume this belongs in V2. Do not require automatic PDF/AI interpretation.

## 8.8 Project Context Reuse Across Tools

Hypothesis:

Repeatedly entering the same:

- quilt dimensions;
- fabrics;
- seam allowance;
- WOF;
- stock;
- component counts;

creates avoidable friction.

Research which cross-tool reuse materially improves normal quilting work.

Integration must be explicit and overrideable.

## 8.9 Additional Painful Workflows

Conduct broad research beyond the hypotheses above.

The desired result is not:

> “We validated most of the list.”

It is:

> **“We found the strongest actual jobs after testing both the listed hypotheses and unanticipated alternatives.”**

A newly discovered workflow may replace a hypothesis in this brief.

For every proposed major utility family and workflow:

- map representative head queries;

- identify dominant result types;
- test specialist-tool SERP viability;

## 9.1 Demand After Substitution

SEO demand must not be evaluated in isolation from competitive alternatives.

For each major opportunity ask:

# 17. V2 Design Principles to Preserve Unless Evidence Refutes Them

## 17.1 Complete, not bloated

Breadth should reduce the need to leave QuiltClarity.

Do not create fifty unrelated calculator cards.

Use:

- taxonomy;
- contextual next actions;
- project integration;
- good search/discovery.

## 17.2 Solve jobs, not formulas

A formula gets a standalone tool only when that is actually the user job or a valuable search entry surface.

Multi-step pain should become a workflow solver where appropriate.

## 17.3 Commodity utilities are allowed

Do not demand uniqueness from every calculator.

Ordinary tools can exist because:

- users need them;
- users search for them;
- they build trust/completeness;
- they feed larger workflows.

## 17.4 Differentiation must be real at the system/workflow level

Do not call:

- cutting diagrams;
- mixed-size optimization;
- free;
- no-login;
- calculator breadth

unique without evidence.

## 17.5 Integration removes repeated work

Reuse known context safely. Never hide assumptions. Allow overrides.

## 17.6 One engine, multiple valid entry points

Avoid duplicate calculation logic. Separate UX/search surfaces may share domain engines.

## 17.7 Defaults are convenience, not truth

Keep current domain discipline.

## 17.8 Trust beats false precision

Explain:

- what is known;
- what is assumed;
- what is optimized;
- what is not guaranteed.

Do not claim global optimum without proof.

## 17.9 Free-web/no-login is supporting advantage, not moat

Assess durable value from:

- useful breadth;
- integration;
- strong workflows;
- correctness;
- explainability;
- speed;
- search footprint;
- tests/domain knowledge;
- repeat use.

## 17.10 Do not bloat to defend against copying

Copyability is not a reason to add unrelated features.

Use the copy/absorption test to understand durability, not to create feature sprawl.
