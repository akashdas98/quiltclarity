# V1.1 Cut-list Compiler

## Decision

Use one project-level cut-requirement editor backed directly by schema-version-2 `PlannerProject.cutRequirements`.

- Desktop uses one semantic table ordered `Fabric | Piece | Qty | Width | Height | Cut/Finished | More`, with each visible label directly above its control and the semantic header retained visually hidden for table navigation.
- At 800px and below, the same mounted rows become labeled editable groups separated vertically without nested side borders/padding; labels and controls share a row while each unprefixed field error aligns beneath its control. At 650px and below, labels stack above full-width controls and the error remains unprefixed beneath the control. No duplicate responsive form tree is mounted.
- A new row inherits only visible context that reduces repetition: the preceding fabric assignment and cut/finished mode. Quantity and both dimensions remain visible with explicit defaults.
- Row actions support last-row Enter/add, duplicate, delete with one-step undo, and advanced rotation/orientation/WOF/notes fields.
- The final cut row may be deleted. The editor presents an actionable empty state and preserves one-step undo; calculation remains blocked by project validation until at least one requirement exists.
- Requirement errors retain `aria-invalid`, summary linkage, and focus on the first invalid field. Desktop adds one full-row, vertically listed error region with field-name prefixes; card breakpoints display the same errors per field instead. Editing an invalid control removes only its stale linked presentation, while successful recalculation clears every residual validation node and state before focusing results.
- Tabular import deterministically auto-detects tab/newline-separated spreadsheet cells or comma-separated CSV with standard quoted fields. Both formats use the documented six columns or recognized headers, parse explicit decimal/fraction/unit syntax, validate every cell, require explicit mapping for unmatched fabric names, preview all rows, and compile requirements only after confirmation.

## Rationale

The former fabric-owned piece subforms made a 20–40-row external pattern behave like dozens of separate forms and preserved a second controller data shape after persistence had normalized. One mounted semantic editor gives keyboard and mobile users the same ordered task while keeping fabric assignment explicit. A pure deterministic compiler makes paste behavior testable and prevents ambiguous prose inference or UI-only parsing rules.

## Consequences

- The planner controller, persistence adapter, calculator transfer, and project domain share one canonical project model.
- The parser remains framework-, DOM-, storage-, analytics-, and optimizer-independent.
- Unmatched or duplicate fabric names never resolve silently; user mapping is required.
- Malformed quoting, dimensions, quantities, modes, and column counts block import but do not discard pasted source.
- Pasted content remains local and is never included in analytics. M8 may add only closed categorical paste-action events, never rows, names, labels, measurements, quantities, or mappings.
- Stock/pattern inputs and reconciled stock-plus-purchase results remain scheduled for M6; M5 retains the coherent fresh-bolt result contract.
