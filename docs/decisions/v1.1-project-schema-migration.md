# V1.1 Project Schema Migration

## Decision

Use schema version 2 for both the `quilter:planner-state` envelope and its persisted V1.1 project. The canonical project model owns:

- a stable local project ID and schema version;
- unit system and default seam allowance;
- top-level fabric plans with optional pattern references and project-local stock pieces;
- top-level cut requirements assigned by `fabricId`;
- explicit `orientation` and `isWofStrip` values on every requirement.

Valid version-0 and version-1 nested projects migrate losslessly by flattening each fabric's piece groups into assigned cut requirements, adding empty stock arrays, and leaving pattern fields absent. The migration does not synthesize or alter dimensions.

M5 retired the temporary nested controller draft. The cut-list UI, domain planning, calculator transfer, and persistence now use schema version 2 directly.

## Rationale

Finite-stock reconciliation and rapid project-level cut entry require stable fabric assignment independent of UI nesting. Making the normalized model authoritative in M1 prevents later optimizer, persistence, and UI milestones from building parallel project representations.

Preserving the former form through M1-M4 avoided mixing schema migration with the M5 interaction redesign. Removing those adapters at M5 prevents the temporary shape from becoming a parallel project model.

## Consequences

- Current valid saved projects restore automatically and retain fabric settings, piece fields, labels, notes, rotation/orientation constraints, units, and seam allowance.
- Migrated projects default to no stock and no pattern comparison, so fresh-bolt planning remains available without semantic changes.
- Corrupt or incompatible raw local state is no longer deleted during restore. The UI reports that automatic recovery failed, while the original value remains available until the user deliberately saves a replacement.
- A structurally valid schema-version-2 project inside an unknown numeric envelope is recovered, rewritten into the version-2 envelope, and reported with an explicit issue.
- Calculator-to-planner transfer appends an assigned top-level cut requirement.
- The project-level cut-list controller reads and writes assigned top-level cut requirements without compatibility adapters.
- M2 and M3 must consume the existing stock and pattern fields rather than introduce alternate schemas.
